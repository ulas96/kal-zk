## Manual and analytical decisions

### ZK-CIR-016 — flattened-form review

Reviewer `ulas96` compared both numbered `@dev Flattened form` lists with `Define()` statement by
statement after the threshold-domain fix. `KnowledgeCircuit` has three statements in the documented
order. `MembershipCircuit` has nine statements in the documented order: both 64-bit decompositions
precede the comparison; leaf/path/root, nullifier/audience and challenge bindings use the operands
listed. Result: reviewed, no divergence.

### ZK-CIR-017 — duplicate caller-selected secrets

Decision: unsupported by construction. Public enrollment and issuance generate 31-byte secrets from
the service entropy source; no production API accepts a caller-selected membership secret. Attribute
changes are revoke-and-reissue operations. A new credential therefore has a new secret, nullifier
and pseudonymous account. The operator must explicitly migrate application data if continuity is
desired; `issued_to` must never become an authentication link.

### ZK-SQL-002 — PostgreSQL compatibility

The supported matrix is PostgreSQL 14 and 18, using a non-superuser database owner on both. The
migrations use unqualified identifiers, require no extension, and are applied through `search_path`.
PostgreSQL 13 is not claimed because it is upstream end-of-life. Evidence is the `postgres` CI matrix
for the signed tag; every discovered `TestDBZK*` test must pass and none may skip.

### ZK-INV-004 / ZK-INV-009 — phase and release gates

The Makefile distinguishes the no-database developer run from the database/audit runs. `make check`
is the phase boundary; `make release-check RELEASE_TAG=v0.1.0` is the publication boundary and adds
audit-tag tests, mutation evidence, module hygiene, full-history checks and signed-tag verification.
The CI workflow discovers the complete `TestDBZK*` set rather than accepting one matching pass.

### ZK-INV-006 — control ledger reconciliation

The register has exactly 147 unique IDs. `TestZKINV003ExternalCaseCoverage` parses every external
test's `Covers:` header and this evidence report; duplicate, unknown, roadmap, partial and blocked IDs
are failures. The stable release ledger is therefore **147 covered/evidenced, zero roadmap, zero partial, zero blocked**.
`SECURITY.md` points operators to both the register and this signed evidence.

### ZK-SES-008 — root fingerprinting analysis

The anonymity set for a proof is the intersection of live credentials and credentials present at the
client-named root. With enrollment rate `lambda`, grace window `G`, and a root lag of `delta <= G`,
the expected exclusion from the newest live set is approximately `lambda * delta`, before revocation
effects. A client naming an older accepted root therefore discloses a synchronization/enrollment
window. This is a disclosure to document, not a value the protocol can hide.

## Operational decisions reconciled from the register

- One-shot claims exist only in the request-local holder. They may satisfy the action in the request
  that proves them; later requests and new sessions do not inherit them.
- Recurring claims bind to the session. A conjunction may be assembled with distinct credentials;
  it is not a proof that one secret satisfied every claim.
- Credential revocation prevents new proofs after root grace. It does not revoke an already-issued,
  unlinkable pseudonymous session; operators call session revocation separately when required.
- Response delivery cannot be atomic with credential issuance. Internal failures roll the database
  transaction back. If delivery fails after commit, the issuer compensates with the returned leaf
  index and `RevokeCredential`.
- `deploymentID` is stable and globally unique. Changing it intentionally rotates every audience and
  pseudonym.
- Each threshold result discloses one policy bit. Several thresholds over one attribute compose into
  a narrower bracket.

## Evidence record

The signed tag's Actions run records the commit SHA, toolchain and PostgreSQL versions, exact DB-test
reconciliation, audit-test output, govulncheck, gosec and `git verify-tag`. R1CS fingerprints,
benchmark output, the mutation manifest and its JSONL results are uploaded as named workflow
artifacts. Publication is blocked if a required job or signature check is non-zero.
